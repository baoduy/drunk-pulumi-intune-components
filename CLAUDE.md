## Project purpose

`@drunk-pulumi/intune-components` is a Pulumi component library for Microsoft Intune. It sits on top of the
Microsoft Graph API and the `drunk-pulumi` component conventions (see `src/base/`, shared with sibling
`drunk-pulumi` packages) and re-exposes raw Graph resources as small, typed, composable Pulumi components.

The goal is: a consuming stack writes one nested config object (see `IntuneManagementArgs` in
`src/IntuneManagement.ts`) instead of hand-rolling Graph API calls. Components apply secure defaults
(e.g. personal device enrollment is blocked by default when macOS is configured — see
`createPlatformRestrictions` in `src/IntuneManagement.ts`) while every default stays overridable through
the args, and unconfigured pieces (antivirus, disk encryption, firewall, custom configs, catalogs, ...) are
simply omitted rather than forced.

## Commands

```bash
pnpm install                 # install deps
pnpm run build               # update-tsconfig -> fastBuild (tsc) -> copy package.json/README/PulumiPlugin.yaml to bin/
pnpm run fastBuild            # tsc only, faster inner-loop build
npx tsc --noEmit              # type-check without emitting — run this after any change
pnpm run test                 # jest (no test files exist in this repo yet)
pnpm run docs                 # ts-node ./.tasks/generate-docs.ts
pnpm run update                # npm-check-updates -u && pnpm install
```

- `tsconfig.json`'s `files` array is generated by `.tasks/update-tsconfig.ts` (run via `pnpm run
  update-tsconfig`, part of `build`) — it lists every file under `src/` explicitly. If you add a new
  source file, run `pnpm run build` (or that task directly) or the new file won't be compiled/exported.
- `pulumi-test/` is a standalone example Pulumi stack (its own `package.json`/`tsconfig.json`) used to
  hand-test the built component API. `cd pulumi-test && npx tsc --noEmit` to sanity-check usage against
  the library's public types. It currently imports `OriginCertResource`, which doesn't exist in this
  package (`src/index.ts` only exports `IntuneManagement` and `devices`) — treat that file as stale unless
  you're updating it alongside a real change.
- Graph API calls resolve credentials via `createCredential` in `src/helpers.ts`: if `INTUNE_AZURE_TENANT_ID`,
  `INTUNE_AZURE_CLIENT_ID` and `INTUNE_AZURE_CLIENT_SECRET` are **all three** set, an explicit
  `ClientSecretCredential` is built from them; otherwise (including any partial mix with `AZURE_*` names)
  `DefaultAzureCredential` is used, which reads the unprefixed `AZURE_*` vars and also supports managed
  identity, workload identity, Azure CLI login, and OIDC federation. `.devcontainer/.env-sample` lists the
  full env shape used for local dev.

## Architecture

Two layers, both building on `src/base/`:

1. **Dynamic resources** (`src/devices/*.ts`, e.g. `ConfigurationPolicy.ts`, `MacCompliancePolicy.ts`,
   `CorporateDeviceIdentifiers.ts`, `DeviceCatalogs.ts`) — each file pairs a `XxxProvider extends
   BaseProvider<TInputs, TOutputs>` (implements `create`/`update`/`delete`/`diff` as raw Microsoft Graph
   REST calls through `graphRequest`) with a `XxxResource extends BaseResource<TInputs, TOutputs>`, a thin
   `pulumi.dynamic.Resource` wrapper. This is the direct Graph-API-to-Pulumi-resource mapping; it knows
   nothing about "simple config" or defaults, only the Graph payload shape.

2. **Components** (top-level `src/*.ts`: `IntuneManagement`, `DeviceConfiguration`,
   `DeviceCustomConfiguration`, `DeviceCustomConfigurationImporter`) — each `extends
   BaseComponent<TArgs>` (a `pulumi.ComponentResource`) and composes one or more dynamic resources plus
   their assignment resource into a single developer-facing unit. `IntuneManagement` is the entry point a
   consumer instantiates; internally it fans out into the other components based on which optional args
   are present (see `createMacPolicies` in `src/IntuneManagement.ts`).

Supporting pieces:

- `src/devices/helpers/*` (`createMacCompliancePayload`, `createMacAntivirusPayload`,
  `createMacDiskEncryptionPayload`, `createMacFirewallPayload`, `createMacCustomConfig`) — pure functions
  that translate the simplified args a developer supplies into the exact Graph payload
  (`ConfigurationPolicy`/`CustomPolicy` settings JSON) the dynamic resource needs. This is where
  security-by-default values and Graph-specific translation logic belong, not in the components.
- **Assignment wiring**: assignment resources (`CompliancePolicyAssignmentResource`,
  `ConfigurationPolicyAssignmentResource`) are always created with `dependsOn`/`deletedWith` pointed at
  their policy resource, and their args type omits the linking id/type fields (e.g. `Omit<...Inputs,
  'configPolicyId' | 'configType'>`) — the component computes those; callers only supply group targeting.
- **Naming**: child resource names are `${this.name}-<suffix>`, with user-supplied names sanitized via
  `.replace(/\s+/g, '').toLowerCase()` before use in a resource name (see `importMacCustomConfigs`,
  `createDeviceCatalogs`).
- **Pulumi resource type strings** are namespaced as `drunk:intune:<Type>` — `BaseComponent` does this
  via `getComponentResourceType` in `src/base/BaseComponent.ts`; dynamic resources hardcode the same
  `drunk:intune:...` prefix themselves.
- `src/types.ts` has the shared generic helpers (`AsInput<T>`/`AsOutput<T>` map a plain type to its
  `pulumi.Input`/`Output` equivalent recursively) used throughout `devices/` and top-level component args.

When adding a new Intune policy type, the pattern is: add a provider+resource pair under `src/devices/`,
export it from `src/devices/index.ts`, add any payload-building helpers under `src/devices/helpers/`, then
wire it into a `BaseComponent` (either a new top-level component or a new branch in `IntuneManagement`).
